One Harness, Six Ways to Work

How the team harness evolved, and how different models responded

One harness offered six models the same collaboration tools. They used them very differently. We show the final prompt, tools and submission contract, trace the repairs from lost work to realistic testing, then compare who formed teams, who stayed solo and who coordinated the final choice. A new training-credit audit asks which agents carry learning signal.

The same harness did not produce the same kind of team

Part 6 explained how our agents fork, message, adopt code and submit. The next experiments asked a harder question: which of those possibilities would different models actually use?

On one selected twelve-task screen, Sonnet and Opus reached almost identical as-graded scores. Sonnet worked alone in about half its episodes. Opus almost always forked a peer. The score hid a large behavioral difference.

What the final harness actually gives an agent

Here is the final screened collective-intelligence (CI) harness: SOP v7, a commit-based final answer and a local runner that reproduces the judge’s resource limits. A later v8 prompt was drafted to improve comparisons, but it was not the version used for the six-model results below.

Every agent receives the same protocol and has the same rights. There is no fixed planner, coder or manager. The episode has a shared 30-minute deadline and per-agent generated-token allowances; tool results show remaining time and tokens. Forking is available, rather than required by an enforced team-size gate.

The shared views provide the other half of the interface: an agent roster, a message log, a commit log and read-only views of each peer’s files. This lets a model inspect actual code instead of trusting “mine is better” messages. A child can inherit the caller’s context and current assumptions, so an explicit request for a different approach is an attempt to create diversity, not proof that it happened.

Version 7 also separates execution feedback from task reward. The local runner can reveal a timeout or crash. It cannot tell the team how its algorithm ranks on the hidden tests. A local objective number is evidence produced by the team’s own checker, with all the measurement risk that implies.

The prompt is a work protocol, not a role assignment

The SOP is prepended to every agent’s system prompt. Short reminders also appear in the fork, message and submission descriptions, and deadline notices repeat the convergence procedure. These are repeated instructions at decision points, not just an opening essay the agent can forget.

The prompt below summarizes the actual v7 contract used in the screen. Its six steps connect algorithmic exploration to one submitted artifact.

Read the full SOP v7 prompt used for this screen

This is the team SOP rendered for a 30-minute episode. It sits alongside the ordinary task, tool and budget instructions. Agent-visible filesystem paths are retained because they define the interface.

TEAM SOP. Every agent on this team follows these steps. There are no roles and no one is in charge. "Time left" below is the time left shown at the end of every tool result, in whole minutes.
1. Split early. In your first minutes, pick different algorithm families (for example greedy construction, local search or simulated annealing, exact search or DP on a reduced problem, a problem-specific heuristic), fork one peer per family and name its family in the direction. No two agents share a family. Every agent, including the first, sends "approach: <family>" to all with send_message as its first action; a fork direction does not count as this post. If a peer has already posted your family, switch to one nobody has taken and post the new one.
2. Checker and tests. Early on, write a checker that computes the problem's real objective exactly as the statement defines it, and a test set: an input generator that covers sizes up to the largest allowed, plus the sample. The sample alone is not a test set. The checker builds solution.cpp alone, the way it is graded: copy only that file from the commit being measured into an empty directory and compile it there, and for an interactive problem run it against an interactor that plays the judge's side, never on a file of the whole input. Commit them in /app (for example under tests/). Before you compare numbers with a peer, agree with them on the inputs and how you measure, and say in every number you post how you measured it.
3. Commit every working version with the message "obj=<value>": its objective on your tests.
4. About every 3 minutes, look at your peers' best commits (/team/commits.log, git log --all), run them on your tests, and build on whichever is better (git cherry-pick or checkout it, or cp the file). Keep improving until the merge point: a first working version is never the final one.
5. Messages carry numbers or failing inputs only, for example "a2 3f9c1e2 obj=1234 on tests/ (my best 1180)" or a failing input with what went wrong. No plans, greetings or praise.
6. Merge. Nobody calls submit_final while time left is more than 6 min. The only exception: every peer has sent "agree: submit <commit>" for the same commit; silence or "unless someone objects" is not agreement. When time left first shows 6 min or less (the merge point), every agent posts "best: <commit> obj=<value>" for its best commit, measured the way you agreed. Once every peer has posted best:, or at time left 2 min, the agent holding the best commit calls submit_final on exactly that commit; if it has not within a minute, any agent submits it. Never submit a commit made after the best: posts or one that no peer has run. A team that does not submit scores 0: if nobody has submitted at time left 2 min and no best: has been posted (for example you are alone), submit your own best commit.

Which parts are enforced?

The runtime enforces the agent cap, separate working copies, read-only peer views, exact-commit selection and the fact that one submission ends the team. The constrained runner enforces its execution limits when the agent uses it. The final judge grades only the submitted artifact.

The SOP asks for distinct algorithms, useful messages, comparable measurements, peer testing and explicit agreement. It does not enforce them. An agent can ignore the runner, skip comparison or submit before everyone agrees. That gap is intentional in this screen: it lets us observe whether a model can use the harness, rather than having a gate perform the cooperation on its behalf.

This also explains the difference from earlier proposal-based versions. There is no acknowledgement gate to reject an impatient submit. A commit makes the result reproducible; the policy must still choose when to finalize and whose commit to trust.

The harness evolved around the failures it exposed

The revisions were not just more collaboration tools. They changed what an artifact meant, what feedback agents could see, when work could be compared and how the episode ended.

Each repair moved a failure boundary. A protected commit could still arrive too late. A shared score could still be wrong. A clear instruction could still be ignored.

An early submit could erase the rest of the team

In the commit-submission baseline, most episodes never forked. When a team did form, an agent could submit its own commit and stop everyone. The regret term saw only candidates that already existed as commits.

That left an unpriced loss: work still being developed by a peer. The final selection could have zero measured regret because the better alternative had never entered the candidate set.

More process was not a smooth path upward

The SOP made the intended loop explicit: split approaches, test, commit working versions, compare peer work and agree on the artifact to ship. Some revisions improved those visible behaviors while scores fell.

Forcing one shared testing script reduced ambiguity, but also gave the team one common failure point. A stale build, a missing dependency or an invalid test could make every agent confidently agree on the wrong evidence.

Version 7 let agents keep their own checkers, while requiring agreement on inputs and measurement before comparing numbers. It also aligned local execution with the grader’s resource rules. Those are different interventions; their contributions are not separated by this screen.

A test should resemble the thing it is meant to predict

Earlier, threaded programs passed local tests and scored zero at grading. Another candidate included a sibling file that existed in the working tree but was absent from the submitted artifact.

We moved those facts into the environment: test the exact committed file in isolation, and execute under the final CPU, memory and wall-clock rules. Better instructions help only if the measurement itself is meaningful.

Watch the behavior behind the average

The same tools supported several working styles. The 9B could fork quickly and then submit too early. The 27B waited, but often delegated too late and also faced a throughput limit. Flash usually ran a larger team. The Claude models mostly preferred smaller groups.

These profiles combine complete-run counts with selected transcript reads. They describe these runs, not permanent personalities of the models.

Good final selection needs more than low regret

Opus stood out for explicit agreement on the exact commit: every early team submission had it. But even those teams often converged onto one algorithm quickly, with a peer acting as tester or optimizer.

Near-zero regret is therefore ambiguous. It can mean careful selection. It can also mean the candidates became almost identical—or that only one was ever created.

The process metric should follow the claim: distinct approaches, useful information arriving in time, peer work surviving, and a justified final choice.

Training the whole team raises a second attribution problem

The new Flash run trains on complete agent chains under the same v7 interaction contract. It samples four tasks with eight team episodes each, keeps four episodes per task and trains two randomly sampled chains per retained team. Group-relative outcome advantage is shared across the team; decision regret is included, while helping credit remains off. Later dynamic sampling favors task groups with reward spread.

That raises a tempting shortcut: if everyone gets the same advantage, perhaps training the initial agent alone is enough. The new audit argues against that shortcut. Forked agents carried almost two thirds of generated tokens in the live snapshot, and the submitted commit belonged to a forked agent in about two thirds of valid teams.

Code authorship told a different story: shared advantage had near-zero association with it, and many positively rewarded forked traces wrote almost none of the submitted code. Yet a useful tester may contribute no lines. Neither code ownership nor an agent’s own draft is a complete measure of helping.

The current scheme was kept. This is a useful negative finding: a reward decomposition that sounds more individual can make the estimator noisier without measuring better cooperation.

At the refreshed snapshot, the Flash run had completed three updates and was training the fourth. It had not established a held-out cooperation gain. Its new FrontierCS team baseline was also partial: 93 of 172 tasks. It should not be treated as a finished benchmark or compared directly with the one-shot scores in Part 7.

What this changes about the next training experiment

Sonnet’s score with frequent solo work and Opus’s score with frequent peer work leave an important comparison open: how much does cooperation add beyond each model’s own solver?

That requires matched solo, independent-sampling and team controls, with the same artifact safeguards and actual resource accounting. A better fallback is a system improvement; it is not automatically learned coordination.

The new Flash team-training run had not established a learned cooperation gain at the snapshot. The finished model screen is evidence about what the harness permits and what policies choose to do with it.

Build the opportunity for useful teamwork, measure whether the model takes it, then test whether training makes that choice pay.

Evidence and limits

Saved experiment readouts through November 1, 2026, about 12:20 Pacific. The historical audits, SOP revision screens and final six-model screen are different cohorts.

The final screen used twelve selected tasks and four episodes per model; several tasks saturated, and screen tasks were reused during protocol development. Open-model labels refer to Qwen3.5-9B, Qwen3.8-27B and Qwen3.8-Flash-Next. Claude models used API default effort. Decoding, execution speed and costs differ; the 27B is throughput-limited. Claude grading used a second route: its cross-check averaged −0.0007 versus the Flash route, with some episode changes around 0.015.

Reader annotations came from selected episodes, with visible actions and text rather than hidden reasoning for the Claude screen. Two Opus judge-failure cases were regraded; the main figure preserves as-graded scores alongside the adjustment. These are system and behavior comparisons, not a causal estimate of learned cooperation.
