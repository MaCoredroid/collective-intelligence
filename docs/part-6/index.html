Fork, Talk, Submit

A team harness, its first RL experiment, and what the failures taught us

What does it mean for a language-model agent to become a team—and can reinforcement learning teach it to cooperate? Our harness lets a shared 9B policy fork its current state, exchange evidence, inspect and adopt peer work, and deliver one final artifact. I first explain those mechanics, then examine our first team-training experiment: whole-episode outcome and cost rewards, with an attempted score-blind LLM judge for collaboration quality. The checkpoint read did not establish a team gain, and judge feedback rarely reached the update. Trace analysis exposed a more concrete gap: teams could find a better program yet lose it through exhausted testing budgets, weak artifact boundaries and final selection. Those findings motivate a revised harness and reward, whose learning benefit remains to be tested.

01 · The organising idea

Let a finding change the rest of the computation

Several agents answering the same question do not automatically form a cooperating team. Independent sampling can produce several completed solutions and select the best afterward. I wanted to study a different possibility: a useful discovery in one branch could change what the other branches do while they are still working.

The harness therefore exposes collaboration as actions available during the episode. An agent can continue alone, fork another agent, send a finding, inspect a peer’s work and choose what to integrate. There is a starting agent, which I call the root, but no separately trained manager or permanent cast of experts. Every agent uses the same checkpoint and can make collaboration decisions within the configured limits.

Analysis · The object being learned is a sequence of decisions

The interesting question is not how much the agents talk. It is whether the right information reaches the right branch early enough to improve what happens next. An incorrect claim can redirect the whole team just as easily as a useful discovery. The harness supplies communication and integration opportunities; training must learn when they are worth using.

02 · Creating a branch

A fork begins from where the parent is now

A fork starts another instance of the policy from the caller’s current conversation and a copy of its working files. The caller also supplies a task message: what the new agent should investigate. This lets the child begin with the existing problem context, failed attempts and draft implementation, rather than receiving only a short description of the original task.

After the copy, the two agents have separate conversations and working trees. The parent can keep improving its candidate while the child explores an alternative or checks an assumption. Either can fork again if capacity allows. The root is the starting point of this changing graph, not a special model with privileged reasoning ability.

A fork does not merge its eventual work back automatically. The parent receives the child’s first final reply as a message, but a report and a code change are different objects. Someone must inspect the result and decide whether to use it.

Analysis · Inherited context buys continuity, not diversity

Copying the state saves repeated explanation, but also copies assumptions. Two agents can share the same mistaken premise or reproduce the same approach. A useful assignment should create a meaningful difference in work: verify an invariant, try a different neighbourhood, investigate a bottleneck. Fork count alone says little about how much independent information the team gained.

The original working directories also provided a weaker boundary than their names suggested. A child had its own branch but could still write another agent’s files. The redesign makes the root’s files read-only to children and provides explicit adoption. That turns an accidental overwrite into a deliberate integration decision.

03 · Moving information

A message arrives at the next decision

Agents can address one peer, a named group or all other eligible agents. Delivery is asynchronous. The recipient finishes its current tool work, then sees pending messages at its next turn boundary. The sender can continue instead of waiting for a synchronous conversation.

This timing matters. Sending a warning does not interrupt code already being executed. A direct message can wake an idle agent while the team remains active and a slot is available; it cannot revive an episode that has already ended. The child’s first final reply is also sent back to its parent, so completing a branch produces a natural handoff.

The shared whiteboard serves a different purpose. Entries are append-only, and agents receive notice of unread material that they can choose to read. A broadcast addresses current recipients; a board entry remains available for later inspection. Neither creates a single shared mind: each agent still decides what to read, trust and retain in its own context.

Peer search and recent-action views let an agent inspect recorded work behind a summary: tool calls, tool results and visible replies. They do not expose a peer’s hidden reasoning. This is useful when a message says “the fix works” but the recipient needs to see what was actually changed or tested.

Analysis · A report should carry evidence that another branch can use

A useful handoff identifies the candidate, the checks performed and the limits of the claim. “I found a better method” leaves the recipient to reconstruct everything. A specific artifact plus a reproducible check gives the recipient something to verify and adopt. In the traces, I distinguish a message being sent, being delivered and being followed by a relevant action; those are separate links in the proposed benefit.

04 · Turning a finding into work

A message does not merge code

Communication changes what an agent knows. Integration changes the program it will deliver. The original harness let agents inspect files and branches, commit their own work and merge peer changes. It did not automatically combine every child’s output or decide which branch was better.

The revised harness makes that choice more explicit. A child develops a candidate in its own writable workspace; another agent can adopt exact bytes, including a candidate identified by its graded version. Isolation protects the current solution, while adoption provides the route for useful work to enter it.

Analysis · Preserve the connection between evidence and artifact

A score belongs to the program that was tested. If code changes afterward, the old score does not certify the new version. A content hash is simply a fingerprint of the exact bytes: it makes “use the tested program” precise. It does not prove correctness or make a test representative, but it prevents a mutable filename from silently changing the object under discussion.

The walkthrough is illustrative. It shows one sensible path through the revised harness, not a required script for every episode. The policy can reject a suggestion, keep working independently or decide that another branch is not worth creating.

05 · Ending together

One team submits one concrete result

Testing a candidate and finishing the team are different actions. An online grading call returns feedback and consumes testing opportunity. Team submission chooses what the whole episode will deliver.

In the original pilot, any agent could call team_submit. The harness took a snapshot of that agent’s current working tree, including uncommitted changes, stopped work across the team and used that snapshot as the final artifact. It did not require a majority vote or automatically select the highest earlier grade. If no agent submitted, the original fallback used the root’s files.

The revised protocol starts with a graded proposal. An agent cites a real candidate’s content hash and verified online feedback. An eligible peer can acknowledge that specific proposal or object with a different graded artifact whose score is at least as good. A qualifying unresolved objection blocks the affected proposal; it is not a vague veto over every possible submission.

Review attaches to the named version. Editing a working file after an acknowledgment does not change the bytes that acknowledgment referred to. The host checks the identity and grading record, resolves the eligible choice and installs the selected bytes as the final artifact for everyone.

A team can also end without a living peer available to acknowledge. Hard deadlines can arrive before agents finish their conversation. The protocol therefore includes no-living-peer and deadline routes, plus a graded-artifact fallback when a valid proposal was not completed. Normal stopping is guarded so that silently abandoning the proposal process is not the easy path. A rescued fallback can still receive a protocol-related charge.

Analysis · Peer agreement and outcome quality answer different questions

The protocol establishes what was proposed, what evidence supported it and which artifact was selected. It does not establish that the program is the best possible solver. In the redesign, agents see online scores on public cases while hidden cases determine the final outcome. A strong public grade remains evidence for the choice, not advance knowledge of its hidden performance.

Automatic fallback is also a real intervention. If it preserves a good program that the agents would have lost, that improves the system. To claim learned cooperation, I still need controls that receive the same preservation and submission safeguards.

06 · The training experiment

Train the whole episode, including its decisions

The action space above made collaboration possible. The next question was whether reinforcement learning could teach the shared policy to use it well. The first experiment trained the original pilot harness: any agent could submit its current files for the whole team. The graded-proposal protocol was a later response to the failures, not a mechanism already present in those training results.

I began with an already trained 9B checkpoint. All agents shared its weights, and the update used group-relative policy optimisation (GRPO) over complete team attempts. The initial training pool had 139 update-eligible tasks; six collaboration-evaluation tasks were excluded from updates. This was a FrontierSmith-centred optimisation study, not the FCS172 one-shot evaluation from Part 5.

The first team-training recipe
ElementWhat was trained or compared
One attemptA complete episode: work, forks, messages, inspection, integration and final submission.
One task groupEight attempts with shuffled agent caps 1, 1, 2, 2, 4, 4, 6, 6; bounded time, tokens and grading.
One updateTwo task groups. Agent and compaction chains share their episode’s team advantage.
Training sequenceTen updates with outcome and costs, then ten more from that policy with a fresh optimizer and an attempted LLM-judge intervention.
Checkpoint readThe starting, ten-update and twenty-update policies, each evaluated in solo and team modes on six held-out tasks × two seeds.

A larger cap allowed delegation; it did not force an agent to create teammates. The first recipe offered no positive reward simply for forking, messaging, reading peers or merging branches. An efficient decision to stay solo could be the right outcome.

Analysis · Whole-team credit is a starting point, not an attribution

The group consists of repeated episodes on a task, not the agents inside one episode. A stronger team return can reinforce the sequences that produced it, but all of those sequences inherit the same team advantage. That does not identify which fork, message or adoption decision created the gain.

The planned same-prefix counterfactual comparison—continue a saved state with and without a particular collaboration decision—was not part of this first recipe. Voluntary forks also happen in states selected by the policy, so forked-versus-solo outcomes are observational. Finally, the continuation’s optimizer resets and evolving judge rules make this a pilot sequence rather than a clean ablation of one reward change.

07 · The reward design

Reward useful work, then audit the judge’s influence

The base objective combined the native score of the submitted program with costs for aggregate work and estimated critical-path latency. Work includes the computation across agents and their tool use. The latency term concerns the dependency path through the episode, rather than adding parallel work as if it all ran sequentially.

R_team = Q_native − λ_work · (team work / work budget) − λ_path · (critical-path estimate / time budget)

Q_native is the normalized verifier score; the result tables later rescale it to 0–100. The budget multipliers balance outcome quality against resource use. They are not rewards for visible activity. A longer conversation or an extra branch has to earn its cost through a better result or a more efficient route to one.

I then tried an LLM judge for distinctions the final score leaves implicit. The judge inspected the task and recorded team behavior without the final native score or hidden reasoning. It ranked attempts within the same task-and-budget group, with evidence references for its judgments. Peer-specific criteria were inapplicable to a genuinely solo trace, so the rubric was not supposed to reward ceremonial collaboration.

What the team rubric tried to recognize
ThemeQuestion posed by the rubric
ExplorationDid branches pursue meaningfully distinct approaches, while allowing productive independent work?
Information and validationWas shared information actually used? Was there evidence before adoption, and were disagreements tested?
Selection and disciplineDid the final choice match the available evidence? Was work productive and safe, with proportionate coordination?

This was advantage reshaping, not a fixed scalar “collaboration bonus” added for each behavior. In the team contract, factors between 0.5 and 1 rescaled eligible positive advantages, followed by renormalization to preserve their total. Nonpositive advantages stayed unchanged. Further trainer guards could reject changes that reversed the return-based ordering. A judge preference could therefore adjust some credit without turning a negatively advantaged episode into a positively reinforced one.

Analysis · A judge signal must survive the path to learning

The early agreement rule required two shuffled presentations to return the same complete tiered order. Across updates 11–16, none of 94 judged teams received shaping. The judge’s real ranking validation had used pairs; exact agreement became much harder on eight-team training groups. A larger output allowance addressed truncation but did not resolve that disagreement.

A later rule used only pairwise preferences that agreed across both presentations. That increased potential coverage in replay, but potential coverage was not the final intervention. After the trainer’s guards and fallbacks, only three of twenty task groups in the ten-update continuation actually applied judge shaping. Those two counts use different units: early teams versus task groups across the whole continuation.

The evidence audit also flagged mistakes in decision grounding and causal timing. A message delivered after an edit cannot explain that earlier edit; a reported grade must belong to the selected version. Hashes and grading receipts make part of this host-checkable. The harder claim—that a message improved what would otherwise have happened—still needs a counterfactual test. More agreement can make a judgment usable without making it true.

This limits the conclusion sharply. The run tests the evolving system that actually trained, but it does not isolate the effect of a strong, consistently applied LLM collaboration reward. The judge’s intended rubric, accepted feedback and measured learning influence must be reported separately.

08 · The measured result

The first sequence did not establish a team gain

The checkpoint read used the same six FrontierSmith tasks held out from team updates, with two seeds per arm. These are native final scores on a 0–100 scale, not the cost-shaped return used for training. “Solo” and “team” mean evaluation modes of each checkpoint; they are not separately trained control policies.

At the later checkpoint, team minus solo was −8.35 points [−14.8, −0.9]. The team’s change from its starting checkpoint was −8.66 [−24.1, +1.2]. The saved 95% intervals bootstrap task-level means, retaining the two seeds within each task. Six clusters still provide limited uncertainty estimates.

Analysis · A lower team score is a result, not a complete explanation

This small read does not establish the collaboration gain I wanted. It also does not establish a general limit on agent teams or a causal penalty from adding the judge. The training sequence changed optimizer and judging conditions, and the semantic intervention reached few groups. The solo read improved at the later checkpoint while the team read fell, which makes the team’s execution and final-selection behavior worth inspecting directly.

Nor does sharing a nominal episode budget establish equal compute. The modes can consume different context, communication and testing work. These are descriptive checkpoint comparisons. A claim about efficient learned cooperation needs a separately trained solo control, matched opportunities and actual work accounting.

09 · What the traces revealed

Discovery, preservation and selection failed separately

The most revealing episode had already tested a much better program than the one it delivered. Its saved online history repeatedly exceeded 72 out of 100 and reached 73.21. The final submitted artifact scored 0.86, consistent with its last online grade. A final score alone would hide the fact that useful work had already occurred.

Finding · A branch can have time left but no way to test

The mechanics audit covered 296 episodes, including 71 forked teams and 86 forks. Forty-one forks began after all eleven shared online admissions were exhausted. The median fork was only about 17% into the wall budget. “Late delegation” here often meant late relative to testing opportunity, not late relative to the deadline.

That matters for the reward interpretation. If a child cannot validate its idea, or its experiment silently replaces the current solution, forking can have poor returns even when an alternative approach has headroom. Reserved tests and protected workspaces make a more meaningful cooperation experiment possible. They do not guarantee a better idea or a successful merge, and a shared write is not by itself proof of harm.

Finding · The submitter often already held the better program

A separate selection audit found loss in 151 of 381 comparable candidate episodes. In every such case, a different, higher-graded artifact had existed before selection. The submitter itself had held a better artifact in 142 cases. A peer had held one in 17, with eight overlapping cases. This broader cohort includes independent-arm candidates counted separately; it is not the mechanics audit’s 296-episode population.

A peer can still challenge a bad choice or remind the submitter of an earlier result. But these counts weaken the explanation that better knowledge was mainly trapped in another agent. More communication is incomplete without artifact memory and a reliable final choice.

Analysis · Headroom does not guarantee cooperation, and rescue is not learning

The retrospective within-task best-of-k uplift over the mean was about 12–15 score points across the audited training cohorts. That suggests there were better complete attempts to discover. It does not prove that an agent could decompose the task, recognize a useful partial result or combine branches within the same budget.

In the original setup, online and final used the same evaluator. All 95 checked exact-hash online/final pairs agreed. Preserving and selecting the strongest verified artifact was therefore an important automatic baseline. If a fallback recovers that lost score, the system improves—but the improvement cannot be credited to learned communication without a comparison that receives the same safeguard.

The selection metric also needs a guard: an episode that never grades anything has no witnessed best to lose. The audit found 33 such episodes among 416 candidates. Missing evidence must not become a cheap way to report zero regret. These observations led to a revised submission-and-reward design rather than a bonus for more forks or more agreement.

10 · What changes next

Repair the opportunities, then test learned use of them

The revised experiment connects the harness repairs to a new training target: reserved child tests, protected branches, explicit adoption and graded proposals, with public online cases separated from hidden final cases. The solo control receives the same submission safeguards and the maximum test entitlement of its paired team cap. Actual usage still has to be measured.

It also adds a small decision-regret term. The selected program’s public score is compared with the best public score already observed; the implemented coefficient is 0.1. The earlier diagnosis’s suggested 0.25 was not the final recipe. Hidden performance remains the outcome target.

Public selection regret = max(0, best observed public score − selected program’s public score)

Using public scores for this component keeps selection loss separate from the public-to-hidden generalization gap. A separate group-based guard handles no-grade or no-valid-proposal endings. A fallback can rescue the delivered artifact while that guard still charges the episode for failing to complete the protocol; this is intentional process shaping, not pure selection regret. The team LLM rubric is demoted to a diagnostic in this redesigned experiment.

Analysis · Mechanical success establishes a path, not the learning result

The redesign has bounded checks. Eight episodes exercised public online and hidden final grading with exact final-artifact bindings; six accepted proposals cited printed hashes without failed proposal calls. A scaled local check completed one optimizer update per arm, checkpoint export and a team-checkpoint reload. Some protocol paths remained unexercised, and the local training check did not qualify the full rollout/training probability-parity gate.

Those checks show that specific paths work. They do not show that the revised reward improves cooperation. The next discriminating comparison is matched solo and team training from the same initialization and task split, plus a team baseline with automatic preservation but no newly learned coordination. I want final hidden scores and actual cost, alongside useful child improvements reaching the final artifact, selection loss and no-grade endings.

The harness defines what agents can do. The reward defines which episodes receive credit. The traces reveal whether either one supports the behavior we meant to teach. Our first attempt did not establish a team gain; it made the next question more precise: can training learn useful propagation and selection once tested improvements can survive long enough to be chosen?
